# Проверка обученной модели на сервере

Эта проверка загружает **обученный `best.pt` ширины 256**, запускает
самостоятельную траекторию и сравнивает каждую частицу с солвером.
Модуль `surrogate.particle.audit` решает другую задачу — проверяет исходные
данные без прогнозов сети.

## Одна команда

После передачи изменений на сервер, из `~/sph-surrogate`, в том же `.venv`:

```bash
bash scripts/evaluate_particle_w256.sh
```

Скрипт использует `checkpoints/particle_history_k256_h8_w256/best.pt` и
отложенный `phi30_c500` из `data`. В журнале выводится фактический шаг
загруженного checkpoint. Лучший checkpoint может быть раньше последнего
шага обучения. Само обучение эта команда не продолжает.

Выполняются три действия:

1. Замер поиска соседей на всех 46 464 целях кадра 8: прежний алгоритм
   против нового, с проверкой точного совпадения ID и масок.
2. Rollout 10 переходов по всему грунту, с известной историей 0…8 и
   прогнозами 9…18. После старта истории пополняются собственными прогнозами.
3. Сравнение всех 16 величин каждой частицы с эталоном в том же кадре и ID.

Новый каталог `checkpoints/particle-eval-w256` содержит:

| Файл | Что смотреть |
|---|---|
| `neighbors.log`, `neighbors.json` | Совпали ли все соседи и как изменилось время поиска на этом сервере |
| `rollout.log` | Шаг checkpoint, рост ошибки положения, ошибки напряжений/давления, время этапов |
| `comparison.log` | RMSE, MAE, p95 и максимальная ошибка каждой величины |
| `rollout_summary.json` | Численные результаты сравнения и худшие частицы |
| `rollout.npz` | Все прогнозы и эталоны для последующего разбора |
| `rollout.png` | Ошибка положения и давление по времени |

Скрипт требует нового каталога результата. Для повторного запуска:

```bash
bash scripts/evaluate_particle_w256.sh checkpoints/particle-eval-w256-repeat
```

## Как понимать результат

В `rollout.log` профиль отдельно показывает `tree`, `neighbors`, `gather`,
`network` и переносы между CPU/GPU. `tree + neighbors` — построение дерева
и поиск, `network` — обработка MLP/GRU. Ускорение поиска не равно ускорению
всего кадра: общий выигрыш зависит от доли поиска во времени.

Профилирование синхронизирует GPU и добавляет накладные расходы. После
выбора настроек окончательную скорость измеряют также без `--profile`.

Это первая проверка на том же коротком окне, что у базовой сети ширины 128.
Она не доказывает точность длинных траекторий и остальных материалов.
Для них меняются `--start_frame`, `--steps` и `--tag` обычной команды
`python -m surrogate.particle.rollout`; нужны отдельные результаты.

## Что изменено в поиске

K=256, история 8+1, веса, нормализация и точный геометрический критерий
сохранены. Поиск теперь выполняется для всех центров кадра блоками по 4096,
а результат раздаётся пакетам нейросети. Исключение самой частицы сделано
операциями NumPy без отдельного Python-цикла для каждой цели.

`--neighbor_workers 4` включает четыре потока CPU; этот параметр не меняет
обучение и архитектуру. В CLI rollout это значение по умолчанию. Библиотечные
вызовы rollout/replay без этого параметра используют один поток.
На следующем кадре дерево и списки строятся заново по новым координатам.
Для 46 464 × 256 результатов ID и маски занимают около 102 MiB CPU-памяти;
временные массивы поиска ограничены размером блока.

37 локальных тестов прошли: добавлены сравнение с полным перебором,
совпадающие координаты, границы блоков, повторный поиск после движения и
совпадение прогнозов при передаче заранее найденных соседей.
Тесты реализации не заменяют проверку обученных серверных весов.

Локальный замер на `phi35_c1000`, все 46 464 цели, K=256, медиана трёх
повторов после прогрева:

| Кадр | Прежний поиск, с | Новый поиск, 4 потока, с | Ускорение поиска |
|---:|---:|---:|---:|
| 8 | 0.978 | 0.325 | 3.01× |
| 100 | 1.026 | 0.326 | 3.14× |
| 159 | 1.047 | 0.327 | 3.20× |

[Исходные замеры и версии библиотек](experiments/local_neighbor_benchmark_2026-09-07.json).
Для сверки обе реализации сохраняют полные массивы ID/масок; прежний rollout
обычно держал только текущий пакет. Построение дерева измерено отдельно.
Это CPU местного компьютера, не время T4 и не ускорение полного rollout.

## Где здесь Project Chrono

В официальном [SphCollisionSystem.cu](https://github.com/projectchrono/chrono/blob/main/src/chrono_fsi/sph/physics/SphCollisionSystem.cu)
есть GPU-поиск: `calcHashD` присваивает частицам ячейки, сортировка группирует
их, `findCellStartEndD` находит границы групп. `neighborSearchNum` и
`neighborSearchID` обходят 27 ячеек и отбирают частицы внутри радиуса `2*h`.
Данные хранятся в
[ProximityDataD](https://api.projectchrono.org/development/structchrono_1_1fsi_1_1sph_1_1_proximity_data_d.html).

Наш код пока использует SciPy на CPU. Для переноса найденного компонента
Chrono потребуется адаптер к его GPU-буферам и сохранение исходных ID.
Кроме того, фиксированный радиус не гарантирует ровно 256 ближайших:
для совместимости с обученными весами поиск по ячейкам должен расширяться
до достаточного охвата и выбирать точные K ближайших. Это отдельная
оптимизация для проверки на CUDA. В текущей правке код Chrono не подключён.
