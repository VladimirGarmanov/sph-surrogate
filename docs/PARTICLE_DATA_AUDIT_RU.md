# Полная проверка данных ParticleNet

`surrogate.particle.audit` читает все доступные значения из грунта, плиты
и стенок и все соседние во времени кадры грунта. Это полный проход, без
случайной выборки частиц или кадров. Массивы открываются только для чтения,
расчёты идут по кадрам; весь датасет в оперативную память не загружается.
Модель и GPU для проверки не нужны.

Сохранён [локальный отчёт phi35_c1000](experiments/local_phi35_c1000_audit.md):
150 394 480 чисел, без NaN/Inf и неположительной плотности. Для сравнения
использованы масштабы из присланного вывода сервера, не скачанный `stats.npz`.
Этот один прогон не заменяет проверку всех 25 серверных материалов.
Разброс изменений скоростей на нём в 5,4–9,6 раза выше присланных масштабов;
причину конкретных TRAIN-пиков это само по себе не устанавливает.

## Запуск на сервере

После коммита, push и `git pull --ff-only`, в другом SSH-терминале:

```bash
cd ~/sph-surrogate
source .venv/bin/activate
nice -n 10 python -u -m surrogate.particle.audit \
  --data_dir data \
  --experiment checkpoints/particle_history_k256_h8_w256 \
  --out_dir checkpoints/particle-data-audit
```

Параметры истории, шага кадров и holdout берутся из `config.json`,
масштабы 16 выходов — из `stats.npz` того же эксперимента. Веса не читаются.
Проверка не останавливает обучение, но чтение данных и вычисления на CPU
могут временно повлиять на его скорость. `nice` снижает приоритет проверки.
В конце каждого прогона печатается прогресс.

Выходной каталог должен быть новым. При повторной проверке выбери другой
`--out_dir`. Без `--experiment` доступны проверки файлов и физических
значений с настройками `Config` по умолчанию; сравнение с нормализацией
тогда не выполняется.

## Что открыть

Сначала **`checkpoints/particle-data-audit/report.md`**: читаемая сводка
на русском с единицами мм, мм/с и кПа. Её можно целиком прислать для разбора.
На сервере:

```bash
cat checkpoints/particle-data-audit/report.md
```

Остальные файлы нужны для подробного анализа:

| Файл | Что в нём |
|---|---|
| `summary.json` | Полные счётчики и статистики каждого прогона, сырых величин, переходов и нормализации |
| `normalization.csv` | Среднее и полный разброс целевых изменений; сравнение с сохранённым масштабом; TRAIN и holdout отдельно |
| `frames.csv` | Каждый допустимый целевой кадр: число частиц, недопустимых пар, крупных изменений и ошибка неизменной частицы |
| `worst_targets.csv` | Самые большие изменения по каждой величине и самые тяжёлые пары: прогон, кадры, номер частицы, значения до/после |
| `invalid_values.csv` | Примеры NaN/Inf и неположительной плотности грунта с точными координатами в массиве |

По умолчанию сохраняются 10 крупнейших случаев **для каждой величины в каждом
прогоне**; число можно увеличить через `--top`. Для NaN/Inf и неположительной
плотности сохраняются первые 1000 примеров на файл. Эти ограничения касаются
только примеров в отчёте: **счётчики и статистики вычисляются по всем значениям**.

## Какие вопросы закрывает проверка

1. **Все ли файлы прочитаны?** Скрипт замечает неполные тройки, неверные формы,
   тип данных и ошибки чтения. Неизвестные NPY-файлы перечисляются отдельно.
   В текущем полном наборе ожидаем 25 полных троек. Отсутствие целого
   обучающего прогона нужно сверять с манифестом: по имеющимся файлам нельзя
   узнать, что такой прогон должен был существовать. Отсутствующие holdout-теги
   из конфига проверяются явно.
2. **Есть ли недопустимые значения?** Считаются все NaN/Inf и случаи
   неположительной плотности грунта. Нечисловые значения исключаются из
   численных статистик с явными счётчиками; наличие проблемы не маскируется нулями.
3. **Насколько редки сильные изменения?** Для каждого выхода считаются все
   случаи, когда `abs(delta) / saved_std` больше 10, 100 и 1000,
   и доля квадратичной ошибки, которая приходится на эти случаи.
   Это пороги для просмотра, а не границы физически допустимого.
4. **Представительны ли масштабы обучения?** Полный разброс допустимых целевых
   переходов TRAIN сравнивается со значениями `target_std`. Например,
   отношение 5 означает, что разброс всего проверенного TRAIN в пять раз
   больше сохранённого масштаба. Нулевой разброс постоянного столбца допустим;
   при подготовке обучающих статистик для него используется масштаб 1.
5. **Где искать причину?** Экстремумы сырых величин в `summary.json` имеют
   номера кадров и частиц; `worst_targets.csv` показывает точные переходы.

## Как считаются переходы и ошибка

Сырые значения и соседние переходы грунта включают все его кадры, даже
если массив плиты короче. Расхождение длин явно выводится в отчёте.

Для сравнения с нормализацией используются ровно допустимые целевые окна
`ParticleDataset`: начальный кадр не раньше `history_frames × frame_stride`,
будущий кадр через `frame_stride`, внутри общей длины грунта и плиты.
Проверяются все начальные кадры, включая разные фазы шага. Неполные или
нечитаемые тройки не включаются в общие TRAIN/holdout-статистики.
Входные масштабы `node_std`/`edge_std` здесь не пересчитываются.

`zero_delta_mse` — ошибка прогноза «оставить частицу неизменной»:

```text
среднее по 16 величинам и полным конечным парам: (delta / saved_std)²
```

Среднее нормализации сокращается при вычитании прогноза из цели, поэтому
для этой ошибки нужен только `target_std`. Это **не loss обученной сети**:
она может правильно предсказывать часть больших переходов.
По этому отчёту нельзя приписать конкретный TRAIN-пик конкретному примеру
без записи фактических входов и прогнозов того шага.

В объединённых статистиках все пары «частица — кадр» имеют одинаковый вес.
При одинаковом числе частиц это соответствует выбору кадров sampler.
Если число частиц между прогонами различается, веса этих распределений
различаются; это нужно учитывать при сравнении масштабов.

## Чего отчёт не доказывает

Большая скорость, напряжение или изменение могут быть физическим событием,
артефактом солвера либо ошибкой экспорта. Большое число само по себе не
служит основанием удалять частицу или менять цель обучения.

В NPY нет исходных временных меток и отдельной колонки ID. `particle_id`
в отчёте — номер строки, который модель считает постоянным ID. Для проверки
сортировки, пропусков кадров, единиц и сохранения исходных ID нужны CSV
или другой исходный экспорт солвера.

Разность между перемещением и интегралом, приближённым по скоростям на
концах кадра, записывается как `endpoint_kinematic_residual`. Большая
разность может возникать при быстрых изменениях скорости внутри 0,02 с.
Это повод посмотреть кадры, а не самостоятельный критерий повреждения.

Текущий `stats.npz`, checkpoint и данные скрипт не меняет. Решение о новых
масштабах или обработке выбросов принимается после просмотра случаев;
оно требует отдельного эксперимента с согласованной нормализацией.
