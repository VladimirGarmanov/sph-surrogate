# Дообучение ParticleNet на собственных прогнозах

Этот режим продолжает обучение готовой модели из `surrogate/particle/`.
Он нужен для ситуации, когда переход по истинной истории получается лучше,
чем самостоятельная прокрутка: ошибки входят в следующие входы, и сеть
постепенно теряет скорость активных частиц.

Веса берутся из существующего checkpoint. Архитектура, число соседей,
длина истории, шаг времени и нормализация сохраняются. Для рабочей модели
это 256 соседей, 8 предыдущих кадров плюс текущий и 16 предсказываемых
изменений за 0,02 с.

Зафиксированный эксперимент `checkpoints/particle-replay` относится к
исходной сети **hidden=128**, после 20 000 шагов обычного обучения.
Из трёх циклов `best.pt` выбрал цикл 2: ошибка скорости активных частиц
снизилась с 8,9623 до 7,7587 мм/с, но RMSE положения по окну выросла
с 0,14979 до 0,23230 мм. Это смешанный результат, не подтверждение общего
улучшения. Полная таблица — в [RESULTS.md](../RESULTS.md).

Нынешнее обучение **hidden=256 на 50 000 шагов** — отдельный запуск с нуля
через `scripts/train_particle_w256.sh`. Смена значения `hidden` по умолчанию
не меняет ширину загруженных старых весов: fine-tune читает её из checkpoint.

## Что происходит в одном цикле

1. Выбираются случайный обучающий прогон и допустимый начальный кадр внутри
   него. Истинные предыдущие кадры дают начальную историю.
2. Сеть самостоятельно предсказывает весь грунт на `rollout_steps` шагов.
   Все частицы очередного кадра читают одну и ту же историю. Соседи
   выбираются по предсказанным положениям, их прошлое собирается по ID.
   После начальной истории истинные состояния грунта во входы не подмешиваются.
3. Начальная история и полученные кадры сохраняются как **replay** — набор
   собственных состояний, на которых сеть будет учиться в этом цикле.
4. Выполняются `updates_per_cycle` обновлений весов. По умолчанию 75% обновлений
   используют порции из replay, а 25% — порции с обычной истинной историей
   из обучающих прогонов. Порядок этих обновлений перемешивается. Чистые
   примеры помогают сохранить ранее освоенные переходы.
5. Обновлённая сеть проходит одинаковую проверку на отложенном прогоне.
   Сохраняются результаты и checkpoint. Следующий цикл строит новый replay
   уже обновлёнными весами.

Первый переход траектории начинается целиком с истинной истории. Он не
выбирается для replay-обновлений: каждый такой пример содержит хотя бы один
собственный предсказанный кадр. Поэтому `rollout_steps` должен быть не меньше
двух. Обычные чистые примеры выбираются отдельно, согласно `clean_fraction`.

Плита и стенки задают известные положения и скорости. Их напряжения и
остальные материальные состояния маскируются, как при обычном обучении
и rollout. Отложенный прогон используется для проверки, а не для replay
или чистых обучающих примеров.

## Что сеть должна исправить

Для примера из replay целевое изменение считается так:

```text
цель = истинное состояние следующего кадра − текущее предсказанное состояние
```

Это соответствует обновлению в rollout:

```text
следующее состояние = текущее состояние + предсказанное изменение
```

Например, собственная текущая скорость сети равна 7 мм/с, а истинная
скорость следующего кадра — 10 мм/с. Цель дообучения равна +3 мм/с.
Она должна исправить переход именно от того состояния, которое оказалось
у сети. Формула применяется ко всем 16 величинам, с исходной нормализацией.

Сбор replay выполняется **без градиентов**. При обновлении весов градиент
проходит через один прогноз по сохранённой истории. Обратного
распространения через всю десятишаговую траекторию здесь нет. Это ограничивает
память, но улучшение самостоятельной прокрутки всё равно нужно измерить.

## Где запускать

Запуски ниже предназначены для сервера с рабочими весами и исходными
обучающими и отложенными данными. В примерах исходный checkpoint —
`checkpoints/particle_history_k256_h8/best.pt`, то есть исходная сеть ширины 128.
Если он лежит в другом каталоге, замени только этот путь.

На Mac в проекте есть технические smoke-checkpoint, но нет рабочего
checkpoint после 20 000 обновлений. Проверка кода на таких весах не оценивает
качество рабочей модели. Код, commit/push и pull на сервер выполняются
отдельно; команды ниже сами ничего не переносят и не скачивают.

## Сначала короткая проверка запуска

Из корня проекта на сервере:

```bash
python -u -m surrogate.particle.finetune \
  --ckpt checkpoints/particle_history_k256_h8/best.pt \
  --data_dir data \
  --out_dir checkpoints/particle-replay-check \
  --cycles 1 \
  --rollout_steps 2 \
  --updates_per_cycle 20 \
  --batch 32 \
  --inference_batch 32 \
  --lr 1e-5 \
  --clean_fraction 0.25 \
  --val_tag phi30_c500 \
  --val_steps 2 \
  --device cuda
```

Этот запуск проверяет сбор replay, обновление весов, валидацию и сохранение.
Два шага не проверяют устранение деградации на десятом шаге. При истории
из девяти кадров в такой короткой проверке большинство кадров входного окна
ещё остаются истинными.

Используй новый выходной каталог: исходный checkpoint и его каталог нужны
для честного сравнения и повторения эксперимента.

## Основной эксперимент

После успешной короткой проверки:

```bash
python -u -m surrogate.particle.finetune \
  --ckpt checkpoints/particle_history_k256_h8/best.pt \
  --data_dir data \
  --out_dir checkpoints/particle-replay \
  --cycles 3 \
  --rollout_steps 10 \
  --updates_per_cycle 500 \
  --batch 32 \
  --inference_batch 32 \
  --lr 1e-5 \
  --clean_fraction 0.25 \
  --val_tag phi30_c500 \
  --val_steps 10 \
  --device cuda
```

Это три цикла и суммарно **1500 обновлений весов**. В начале каждого цикла
случайно выбирается новый обучающий прогон и начальный кадр. Внутри цикла
обучение использует уже собранный replay; после каждого обновления он
не пересчитывается.

При старте нового эксперимента создаётся новый Adam с постоянным
`lr=1e-5`. Из исходного checkpoint загружаются обученные веса и статистики,
а старые моменты оптимизатора и расписание скорости обучения не продолжаются.
В каждом цикле из 500 обновлений 375 используют replay и 125 — чистые порции.
При других настройках число чистых обновлений округляется до целого;
как минимум одно обновление цикла всегда использует replay.

`batch=32` задаёт число целевых частиц в обучающей порции.
`inference_batch=32` задаёт размер порции при построении полной траектории
и её проверке. Оба режима обрабатывают все необходимые соседские истории;
разбиение на порции не заменяет полный грунт маленьким пространственным участком.

Сбор replay и валидация требуют самостоятельного прогноза **всех частиц**.
В приведённом запуске это 10 кадров исходной проверки плюс
`3 × (10 + 10)` кадров сбора и проверки — всего **70 полных предсказанных
кадров**, помимо обновлений весов и чистой валидации. Эти этапы могут
занимать основное время. Дообучение не обещает ускорения инференса.

Дополнительные настройки по умолчанию:

| Параметр | Значение | Смысл |
|---|---:|---|
| `val_start_frame` | `-1` | Начать фиксированную проверку с `history_frames × frame_stride`; для рабочей модели это кадр 8 |
| `active_speed` | `0.001` | Порог истинной скорости активной частицы, м/с: 1 мм/с |
| `log_every` | `50` | Период записи обучающей ошибки в обновлениях весов |
| `seed` | `17` | Начальное состояние генераторов случайных выборок |

В командах выше `val_tag=phi30_c500` и `device=cuda` заданы явно.
Без `val_tag` выбирается первый доступный отложенный прогон; без `device`
устройство выбирается автоматически.

## Что означает `best.pt`

До первого обновления исходная сеть проходит отложенную проверку. Этот
результат становится исходным уровнем сравнения, а исходные веса — первым
`best.pt`. Поэтому первая дообученная версия не объявляется лучшей автоматически.

После каждого цикла сеть проходит тот же отложенный прогон, с теми же
начальной историей и горизонтом. Дополнительно проверяются обычные переходы
по фиксированным истинным входам. При стандартном `val_samples=16`
из checkpoint и `batch=32` это 512 целевых частиц; эти примеры берутся
из отложенных прогонов.

Основной критерий выбора `best.pt` — **RMSE вектора скорости активных
частиц** в самостоятельной прокрутке. Активность определяется по истинной
скорости солвера, с порогом `active_speed`. Поэтому сеть не может улучшить
эту оценку, просто объявив ошибочно заторможенные частицы неактивными.
Если активных частиц в выбранном окне нет, явно используется ошибка скорости
по всему грунту.

Критерий считается по **всем парам «частица — предсказанный кадр» выбранного
окна**, прошедшим порог активности, а не только по последнему кадру:

```text
sqrt(mean(||v_pred − v_true||²))
```

Начальная истинная история в эти пары не входит. Единица критерия — м/с;
в консоль он выводится в мм/с. В журнале `score_m_s` хранит критерий,
а `selection_metric` показывает, применялась ли маска активных частиц.

При оценке результата обязательно смотри вместе:

- ошибку скорости активных частиц и отношение предсказанного модуля скорости
  к истинному: исчезло ли затухание;
- ошибку положений: не разъехались ли частицы после исправления скорости;
- ошибки напряжений: не потеряла ли сеть качество других выходов;
- чистую одношаговую валидацию: сохранились ли переходы по истинным состояниям.

Улучшение критерия `best.pt` не гарантирует улучшения всех 16 величин.
Короткая проверка одного отложенного материала также не доказывает качество
длинной траектории или остальных материалов.

Подробные значения записываются в `metrics.jsonl`: `active_speed_ratio_median`,
`position_rmse_m`, `position_p95_m`, `position_max_m`, `last_position_rmse_m`,
`feature_rmse` и `clean_one_step`. Отношение модулей скорости хранится как
число, а не процент: `0.38` означает 38%. Порядок `feature_rmse`:
`x, y, z, vx, vy, vz, rho, p11, p22, p33, shear12, shear13, shear23, pc, Ev, Sv`.
Ошибка тензора отдельной нормой здесь не вычисляется: доступны RMSE каждой
его компоненты в исходных единицах.

Если исходный checkpoint обучался с пустым `holdout`, режим печатает
`TRAIN_DIAGNOSTIC`. Тогда исходная и последующие проверки идут на обучающих
данных; `best.pt` и `validation_best.npz` не создаются. Это техническая
диагностика. `val_tag` должен принадлежать отложенной части checkpoint,
а при её отсутствии — обучающей части.

## Сохранённые файлы

Все файлы относятся к новому `out_dir`:

| Файл | Содержимое |
|---|---|
| `finetune.json` | Настройки дообучения |
| `metrics.jsonl` | Журнал обучающих и проверочных метрик |
| `model.pt` | Последнее сохранённое состояние дообучения, для продолжения |
| `best.pt` | Веса с лучшей отложенной оценкой, включая исходный baseline; только при наличии holdout |
| `validation_before.npz` | Самостоятельная прокрутка исходной сети до обновлений |
| `validation_latest.npz` | Проверка последнего завершённого цикла |
| `validation_best.npz` | Результат версии, выбранной в `best.pt`; только при наличии holdout |

## Продолжение с границы цикла

Чтобы довести тот же эксперимент с трёх циклов до пяти:

```bash
python -u -m surrogate.particle.finetune \
  --resume checkpoints/particle-replay/model.pt \
  --cycles 5
```

`cycles=5` — **общее число циклов дообучения**, поэтому после завершённых
трёх добавятся ещё два. При продолжении восстанавливаются веса,
оптимизатор, счётчики и состояния случайных выборок. Новый replay строится
на следующем цикле. Сохранение происходит на границе полного цикла.
Если процесс прерван посередине сбора replay, обновлений или проверки,
`--resume` из последнего `model.pt` повторит этот незавершённый цикл целиком.
Начальный `model.pt` создаётся ещё до исходной проверки, поэтому её прерывание
тоже можно продолжить через `--resume`: исходная проверка выполнится заново.

Гиперпараметры обучения и критерий проверки при `--resume` менять нельзя:
для нового сравнения нужен отдельный запуск и каталог. Разрешается увеличить
`cycles`, сменить `device` или путь `data_dir`. Списки обучающих и отложенных
прогонов и выбранное проверочное окно должны сохраниться; данные по новому
пути должны соответствовать исходному эксперименту.

Checkpoint дообучения нельзя продолжать через обычный
`surrogate.particle.train --resume`: это другой режим формирования
обучающих примеров. Используй `surrogate.particle.finetune --resume`.

## Отдельная проверка выбранных весов

Формат весов совместим с обычным `surrogate.particle.rollout`:

```bash
python -u -m surrogate.particle.rollout \
  --ckpt checkpoints/particle-replay/best.pt \
  --data_dir data \
  --tag phi30_c500 \
  --steps 10 \
  --batch 32 \
  --device cuda \
  --save_particles --plot \
  --out checkpoints/particle-replay/particles_phi30_c500_10.npz

python -m surrogate.particle.compare \
  --result checkpoints/particle-replay/particles_phi30_c500_10.npz
```

Это дополнительный полный запуск. Он удобен для сохранения и разбора всех
16 величин отдельных частиц. Сначала сравни одинаковое десятишаговое окно
до и после дообучения; затем проверяй больший горизонт и другие отложенные
материалы. Сам факт успешного выполнения команд означает, что механизм
работает технически. Качество подтверждается полученными метриками.
