# Report: Neural Surrogate for Chrono::FSI CRM Soil

## Executive summary

This project investigates whether a neural surrogate can replace part of the numerical computation in Chrono::FSI for a plate-sinkage soil problem. Chrono solves the CRM soil model with GPU SPH. The network receives a short history of a target particle and its neighbors and predicts the state change over one frame.

There are two distinct goals. The current experiment is a full autoregressive rollout in which the network updates the entire soil. The intended project direction is a hybrid Chrono + neural solver, in which the network replaces only a selected sub-computation while Chrono continues to compute the remaining physics. The full rollout is slower than Chrono and accumulates error on moving particles; the hybrid loop has not yet been implemented or benchmarked.

## 1. Physical problem and dataset

The simulated experiment is a bevameter test. A circular plate with a diameter of 0.3 m penetrates the soil at 5 mm/s to a depth of 20 mm. The soil is represented by the elastic-plastic CRM model in Chrono::FSI and discretized with SPH.

Each run contains 4 seconds of penetration: 200 frames at dt = 0.02 s. The initial 0.5-second gravity-settling stage is not included.

| Parameter | Value |
|---|---|
| Friction angle phi | 25, 30, 35, 40, 45 degrees |
| Cohesion | 0, 500, 1000, 2000, 5000 Pa |
| Total runs | 25 |
| Training / holdout | 21 / 4 runs |
| Soil particles | 46,464 |
| Plate markers | 410 |
| Wall markers | 24,855 |
| Frame interval | 0.02 s |

Each particle row contains 16 quantities: position x,y,z; velocity vx,vy,vz; density rho; normal stresses p11,p22,p33; shear stresses shear12,shear13,shear23; and additional solver state variables pc, Ev, Sv.

In the locally available run, rho is constant at 1600 kg/m3 and pc, Ev, Sv are zero. Zero error on these columns does not demonstrate that the network learned their non-trivial physics.

## 2. Network inputs

Each target particle is represented by a nine-frame window: eight previous frames plus the current frame.

The target has 18 features per frame:

~~~text
3 velocity features + 10 state features + 3 one-hot type features + 2 run parameters
~~~

The state contains rho, six stress components, and pc/Ev/Sv. The one-hot type is soil, plate, or wall. The run parameters are phi and cohesion.

Each of K = 256 neighbors adds seven pairwise edge features:

~~~text
dx,dy,dz       relative position
distance       pair distance
dvx,dvy,dvz    relative velocity
~~~

Neighbors are selected dynamically at every step from current coordinates using cKDTree. Their history is gathered by the same particle IDs, so a neighbor is not silently replaced by another particle that happened to be closer in the past.

## 3. Architecture

~~~text
target history (9 × 18)       → MLP → GRU → 256-dimensional vector
neighbor history (9 × 25)     → MLP → GRU → 256-dimensional vector
target + neighbor             → message MLP → 256-dimensional message
all neighbor messages         → mean pooling + max pooling
target + pooled messages      → decoder → 16 state changes
~~~

There is no neighbor-to-neighbor message passing, and the output is invariant to neighbor-list order. The model performs one aggregation round.

With hidden = 256, the model has 1,200,656 trainable parameters. It is one shared model for all particles. Adam updates the complete parameter set at every training step.

The network predicts a change rather than an absolute state:

~~~text
delta = state(t + dt) - state(t)
~~~

The delta is added to the current state during inference.

## 4. Training setup

| Setting | Value |
|---|---:|
| Hidden width | 256 |
| Neighbors K | 256 |
| History | 8 previous + current frame |
| Batch | 32 target particles |
| Initial learning rate | 1e-4 |
| Total updates | 50,000 |
| Normalization statistics | 40 random batches |
| Validation | 16 random batches |
| Hardware | Tesla T4, CUDA |

The one-step MSE is dominated by nearly stationary particles. In the evaluation rollout, only 4.84% of comparisons had a true speed of at least 1 mm/s, but they contributed 99.35% of the total squared position error.

## 5. Full autoregressive rollout

The model was evaluated for 10 predicted frames on holdout run phi30_c500, frames 9–18, corresponding to 0.2 seconds of physical time. The initial input history was true data; later states were generated by the network itself.

| Position metric | Value |
|---|---:|
| RMSE over all particles and frames | 0.1235 mm |
| 95th percentile | 0.0366 mm |
| 99th percentile | 0.1567 mm |
| Maximum particle error | 9.422 mm |
| RMSE at frame 18 | 0.2388 mm |

For particles with true speed at least 1 mm/s:

| Metric | Frame 9 | Frame 18 |
|---|---:|---:|
| Position RMSE | 0.021 mm | 1.069 mm |
| Velocity RMSE | 1.81 mm/s | 12.11 mm/s |
| Predicted speed / true speed | 92% | 47% |

The model is better than a zero-velocity baseline: 8.27 versus 13.21 mm/s. However, it increasingly underestimates motion during autoregressive rollout.

Plate pressure results:

| Comparison | Relative error |
|---|---:|
| Network versus estimator on true particles | 1.02% |
| Estimator on true particles versus solver reference | 16.80% |
| Network versus solver reference | 17.04% |

Most of the discrepancy with the reference pressure curve is already present in the estimator itself.

## 6. Runtime

On the Tesla T4, a full predicted frame takes approximately 54.5 seconds, or about 45 minutes per second of model time.

| Stage | Time | Share |
|---|---:|---:|
| KD-tree and neighbor search | 0.663 s | 1.2% |
| History gathering | 10.728 s | 19.7% |
| Normalization | 6.081 s | 11.2% |
| Host-to-device transfer | 2.939 s | 5.4% |
| Neural network | 33.631 s | 61.7% |

Neighbor search is no longer the main bottleneck. A neighbor history is processed repeatedly for every target center, producing about 11.9 million neighbor histories per frame. The full rollout is approximately 11 times slower than the recorded Chrono runtime.

## 7. Why the error compounds

During training, the network sees true histories:

~~~text
true history → predict next frame → compare with truth
~~~

During autoregressive rollout, it sees its own errors:

~~~text
true history → prediction → prediction from previous prediction → accumulated error
~~~

A velocity error changes positions; positions change neighbors and relative features; erroneous stresses enter the GRU history. The next prediction is therefore made on a state that was rarely present during training.

Position and velocity changes are also predicted independently. A useful additional constraint is:

~~~text
delta_position ≈ dt × (current_velocity + next_velocity) / 2
~~~

## 8. Next test: teacher forcing

A --teacher_forced mode has been added. Before every prediction, the model receives the true history up to the current time. The next frame remains hidden and is used only as the target. This measures one-step error without feeding model predictions back into the history.

~~~bash
python -u -m surrogate.particle.rollout \
  --ckpt checkpoints/particle_history_k256_h8_w256/best.pt \
  --data_dir data --tag phi30_c500 --start_frame 8 --steps 10 \
  --batch 32 --device cuda --neighbor_workers 4 --teacher_forced \
  --save_particles --plot \
  --out checkpoints/particle-eval-w256/teacher_forced.npz
~~~

Low teacher-forced error with poor autoregressive error indicates accumulation. High teacher-forced error indicates a one-step problem in the data, normalization, sampling, architecture, or training. Low training error with high holdout error indicates poor generalization.

## 9. Recommended corrective plan

1. Run teacher-forced evaluation on holdout and training runs.
2. Measure the active-particle fraction across all runs.
3. Add an active-weighted loss based on speed or state change.
4. Train on short self-generated histories through scheduled sampling or replay.
5. Add a kinematic consistency loss between position and velocity changes.
6. Estimate normalization statistics from more frames and particles without removing rare physical transitions.
7. Only then compare larger models or alternative graph architectures.
8. Implement the hybrid Chrono + network loop and benchmark only the computation actually replaced by the network.

Adding more similar, mostly stationary frames can reinforce the imbalance toward inactive particles.

## Conclusion

The model learns small changes and is better than a zero-velocity baseline on the first step, but it does not preserve active-particle motion during an autonomous trajectory. Full replacement of Chrono is not justified by the current architecture. The decisive next experiment is teacher-forced evaluation; the promising final direction is a hybrid solver in which Chrono retains physical integration and the network replaces a measurable sub-computation.
